## What Is Implemented

Core environment:

- Correct Spades+ rules environment with nil/blind nil/bags.
- Fixed action space `0-66`.
- Dict and flat observations.
- Public history in observations: bids, played cards, trick winners, void suits, cards remaining.
- Gym/PettingZoo/Puffer wrappers.

Evaluation:

- `spades-eval-puffer`: greedy checkpoint eval.
- `spades-eval-duplicate`: duplicate head-to-head eval with seat swap, confidence intervals, bid counts, contract failures.
- `spades-eval-bid-ev`: checkpoint eval on EV bidding dataset.

EV bidding:

- `spades-generate-bid-ev`: rollout-EV bidding dataset generator.
- `spades-train-bid-ev`: supervised EV bidding trainer with W&B and progress bars.

Model:

- `SpadesTransformerPolicy`
- Current architecture:
  - `d_model=256`
  - `transformer_layers=6`
  - `attention_heads=8`
  - `ffn_size=1024`
  - `dropout=0.05`
- Heads:
  - play pointer over card tokens
  - bid policy head
  - bid-Q head
  - value/margin heads
  - hidden-owner and void auxiliary scaffolding

Protected PPO:

- `spades-train-puffer` now supports:
  - `--active-only-loss`
  - `--bid-ppo-weight`
  - `--play-ppo-weight`
  - `--freeze-bid-heads`
  - `--bid-anchor-path`
  - `--bid-anchor-weight`
  - `--bid-q-anchor-weight`
  - `--bid-anchor-temperature`
  - W&B flags
- The intended PPO mode is:
  - train play/value via PPO
  - freeze bid heads
  - keep bid policy anchored to EV checkpoint
  - select checkpoints by duplicate eval, not training self-play score

## Current Interpretation

The project has moved past "can EV bidding work?" The answer is yes.

What we learned:

- EV bidding pretraining gives a real duplicate edge over the conservative bot.
- Protected PPO can improve play quickly, as shown by the smoke checkpoint.
- Long latest-vs-latest PPO can drift into bad tactics even when training self-play score looks okay.
- Training self-play `env/hand_score` is not the source of truth.
- Duplicate eval is the source of truth.
- Bid EV regret and bid distribution are guardrails; they did not catch v2 because the failure was play, not bidding.

## Next Engineering Step

Implement periodic checkpointing in `spades-train-puffer`.

Reason: v2 may have had a good intermediate checkpoint, but only the final model was saved. We need a PPO ladder that saves every fixed number of steps/epochs so we can select by duplicate eval.

Add flags:

```text
--checkpoint-interval-steps 131072
--checkpoint-prefix checkpoints/ppo_play_anchor_ladder
```

Suggested behavior:

- Save checkpoint whenever `agent_steps >= next_checkpoint_step`.
- Use zero-padded step suffix, for example:

```text
checkpoints/ppo_play_anchor_ladder_000131072.pt
checkpoints/ppo_play_anchor_ladder_000262144.pt
checkpoints/ppo_play_anchor_ladder_000393216.pt
...
```

- Record saved checkpoint paths in metrics JSON.
- Keep existing `--save-path` final checkpoint behavior.
- Do not alter default behavior unless the new checkpoint interval flag is provided.

After implementing, rerun a 1M ladder from the current best:

```bash
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True \
uv run spades-train-puffer \
  --load-path checkpoints/ppo_play_anchor_smoke.pt \
  --save-path checkpoints/ppo_play_anchor_ladder_final.pt \
  --metrics-path logs/ppo_play_anchor_ladder.json \
  --checkpoint-interval-steps 131072 \
  --checkpoint-prefix checkpoints/ppo_play_anchor_ladder \
  --total-timesteps 1048576 \
  --num-envs 32 \
  --horizon 32 \
  --minibatch-size 1024 \
  --learning-rate 1e-4 \
  --anneal-lr \
  --active-only-loss \
  --bid-ppo-weight 0.0 \
  --play-ppo-weight 1.0 \
  --freeze-bid-heads \
  --bid-anchor-path checkpoints/bid_ev_transformer_v1_5k_s8_stronger.pt \
  --bid-anchor-weight 1.0 \
  --bid-q-anchor-weight 0.05 \
  --wandb \
  --wandb-project spades-rl \
  --wandb-group ppo \
  --wandb-run-name ppo_play_anchor_ladder
```

Then evaluate each ladder checkpoint against conservative with 512 duplicate hands. Keep only checkpoints that beat the smoke checkpoint or at least remain clearly positive.

Evaluation command template:

```bash
uv run spades-eval-duplicate \
  --policy-a checkpoint:CHECKPOINT_PATH.pt \
  --policy-b bot:conservative \
  --hands 512 \
  --d-model 256 \
  --transformer-layers 6 \
  --attention-heads 8 \
  --ffn-size 1024 \
  --dropout 0.05 \
  --output logs/duplicate_CHECKPOINT_NAME_vs_conservative_512.json
```

Bid guardrail template:

```bash
uv run spades-eval-bid-ev \
  CHECKPOINT_PATH.pt \
  --dataset data/bid_ev_v1_5k_s8.npz \
  --d-model 256 \
  --transformer-layers 6 \
  --attention-heads 8 \
  --ffn-size 1024 \
  --dropout 0.05 \
  --output logs/bid_ev_eval_CHECKPOINT_NAME.json
```

Selection rules:

- hard reject if duplicate margin <= 0
- reject if bid EV `policy_regret > 4.5`
- reject if illegal actions > 0
- prefer checkpoints with duplicate raw margin above `+5.21`
- use 2048-hand duplicate only for close comparisons between candidate best checkpoints

## Where This Is Heading

The best PPO checkpoint is not the final agent. It becomes a better base/teacher for the next loop.

Near-term roadmap:

1. Find the best protected-PPO checkpoint by checkpointed ladder selection.
2. Promote that checkpoint as current best.
3. Use current best as a stronger rollout/play policy for new EV or search labels.
4. Add a small league/mixed-opponent trainer so training is not only latest-vs-latest self-play.
5. Add belief-sampled root search and distill search labels into the policy.

Important: protected PPO is currently basic self-play:

```text
latest policy controls all four seats during training
```

There is no league yet. Conservative bot is used only for evaluation, not training.

This likely explains why long PPO can look okay in self-play but collapse in duplicate eval. A future league trainer should mix:

- current policy
- current best checkpoint
- EV checkpoint
- conservative bot
- historical checkpoints

## Notes And Pitfalls

- Do not use `checkpoints/ppo_play_anchor_v2.pt` as a base.
- Do use `checkpoints/ppo_play_anchor_smoke.pt` as current best.
- Keep `bid_anchor_path` pointed at `checkpoints/bid_ev_transformer_v1_5k_s8_stronger.pt` for now.
- Do not loosen bid PPO yet. Use `--bid-ppo-weight 0.0`.
- Use `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` for PPO runs.
- Keep `--minibatch-size 1024`; `8192` OOMed on A6000 with this transformer and bid anchor.
- `spades-eval-duplicate` is slow but reliable. Use 512 hands for iteration, 2048 only for close decisions.
- W&B is useful for training traces, but duplicate eval JSON files are the real experiment record.
